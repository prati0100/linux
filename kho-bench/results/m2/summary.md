Steps where the measured time ratio exceeds the square of the count ratio by more than 10% (faster than quadratic growth): inverted baseline 100000->262144 x7.93 (count x2.62, square 6.87); inverted baseline 1048576->2097152 x5.45 (count x2.00, square 4.00; n=1, flagged b_ssh_timeout (timers from its serial log)); inverted early 100000->262144 x8.01 (count x2.62, square 6.87); inverted early 1048576->2097152 x5.15 (count x2.00, square 4.00; n=1 ok). These are measured as listed; the steps at the largest counts rest on single runs. They are not explained by the code model below (which predicts quadratic); a cache effect from the memmove working set (N x sizeof(struct memblock_region)) is an untested hypothesis. No curve is fitted and nothing is extrapolated.

Mechanism (from the code, mm/memblock.c and kernel/liveupdate/kexec_handover.c): both variants call memblock_reserve() once per radix key, in radix-walk order. memblock_add_range() finds the slot with a binary search (__memblock_search) and then memblock_insert_region() memmove()s every region above the slot up by one. The KHO radix key puts the order bit above the shifted PFN (kho_encode_radix_key: higher order -> smaller key), so the walk visits all keys of one order in ascending address order, then the next lower order. Consequences: contig merges into a few regions (reserved.cnt stays small); alt and random (order 0 only, ascending) append at the end of the array (memmove of 0 regions, linear total); inverted places its order-1 blocks above its order-0 blocks, so the order-1 blocks are walked first and every later order-0 insert lands below all ~N/2 order-1 regions, costing a memmove of ~N/2 regions per insert (quadratic total); mixed interleaves 11 orders and is quadratic in the same way, but generation in kernel A runs out of memory (M1 probe above). The early variant does the same per-key inserts in walk1 (plus the node-page inserts of (c)), so it has the same order dependence as baseline's retrieve. Differences between the variants (see the decomposition above): (a) baseline runs discover (kho_discover_noprsrv) and early does not (contig 8388608: discover 738 ms of the -899 ms early − baseline TTI difference); (b) the struct page init is in retrieve for baseline and in walk2 for early, the same work; (c) early walk1 also memblock_reserve()s every radix node page (kho_early_reserve_node), and those pages sit between the preserved ranges, so each one memmove()s the regions above it (O(nodes x reserved.cnt)). Measured (early, median over ok runs of (reserved.cnt after walk1 − reserved.cnt before walk1 − keys) / nodes, at the decomposition counts): contig 8388608: negative, keys merge (reserved.cnt 248 < keys 8388631); alt 4194304: 0.71 (median nodes 300); random 1572864: 0.68 (median nodes 425); mixed 40960: 0.45 (median nodes 872); inverted 1048576: 0.42 (median nodes 109); so walk1 adds fewer separate regions than keys + nodes (42–71% of the node count where positive; a node page that is adjacent to a reserved range merges into it instead of adding a region, an untested explanation); (d) after walk2, kho_radix_destroy_tree memblock_free()s the node pages again from an array of ~N regions (free_nodes, also O(nodes x reserved.cnt)); baseline frees no node pages during boot. (d), timed as free_nodes, and (c), inside walk1 and not separately timed, are the reasons from the code that early is slower than baseline (p < 0.05, ranges separated) at the listed counts: alt (1048576, 2097152, 4194304), random (1048576, 1572864), mixed (32768); the part of the TTI difference no timer covers is listed as the residual above.
